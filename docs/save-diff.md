# Save-data diffing (`tools/dbpf.py`, `tools/savediff.py`, `tools/sims2_types.py`)

Supports milestone B (save/reload comparison): tell **persistent** state (what a save/reload
must preserve) from **transient** state (timestamps, thumbnails, caches). Standard library only.

## Usage

```
$py = '.venv\Scripts\python.exe'   # from the repo root
& $py -I tools/dbpf.py summary <pkg>                       # counts by type
& $py -I tools/dbpf.py list <pkg>                          # type group instance inst-hi size usize comp
& $py -I tools/dbpf.py extract <pkg> <type> <group> <inst> [--instance-hi H] -o out.bin [--raw]
& $py -I tools/savediff.py <A> <B> [--json report.json] [-v] [--fail-on persistent,unknown]
& $py -I tools/tests/test_savediff.py                      # unit + real-data tests (~4 s)
```

`A`/`B` are two neighbourhood folders or two whole user-data folders (anything laid out the
same way). Files pair by relative path; packages are opened and resources pair by
(type, group, instance, instance-hi). Exit status 1 if anything differs in the `--fail-on`
classes, so it can gate a scenario.

### dbpf.py
DBPF 1.1, index minor 0/1 (5-word entries) and 2 (6 words: instance-hi), the DIR resource,
and QFS/RefPack (9-byte header: compressed size, `10 FB`, 3-byte big-endian size) written from
the public format description. `Package(path).entries` gives type/group/instance/instance_hi,
stored size, `compressed`, `uncompressed_size`; `read(entry)` returns decompressed bytes and
checks the size against the header. `write_package` writes an uncompressed package (used by
the self-check). Every one of the 130,988 compressed entries across all 562 packages of
E001 (including Characters, Lots, Storytelling) decompresses to the size the DIR/QFS header
promises (~33 s in Python).

### Output
Text summary (per class: added / removed / changed, then the individual differences) and a JSON
report: `files` (non-package files and added/removed packages), `packages`, `resources`, each
changed resource with `ranges` (byte `[start,end)` runs, plus a tail run when sizes differ) and,
where a parser exists, `fields` (name, old, new).

Content is compared after decompression, so re-compression alone is not a difference
(counted as `storage_only` per package). DIR is excluded from pairing for the same reason.
Package header timestamps are recorded in the package record, not as differences.

## Classification (`tools/sims2_types.py`)

75 type ids, seen in E001 plus the OpenTS2 constants: **24 persistent, 2 transient, 49
unknown**. Unknown is the default for any id not in the table.

Transient (reason is mandatory and stored with the id):
- `DIR` 0xE86B1EEF: derived from how entries are stored (compression), not from content.
- `BMP_` 0x424D505F: thumbnail/portrait bitmaps, regenerated by the game.
- Files: `Thumbnails/`, `*.png`, `Logs/`, `*.cache`, `*.log`.

Persistent (gameplay-state records; the evidence is the OpenTS2 codec name or the community
description): NGBH and the OpenTS2 `NHOOD_*` types, SDSC (sim description), FAMI (family), SREL
(relationships; name from the community list), the OpenTS2 `LOT_*` types (info, base info, lot
object, terrain, textures, fence posts, pools, roofs, wall graph/layers, string map, 3ARY),
OBJM and the object-save-type table, SIM_APPEARANCE and GZPS.

Unknown on purpose: all scenegraph resources (GMDC, GMND, SHPE, CRES, TXMT, TXTR, 3IDR), IMG,
BINX, strings/BCON/OBJD/SLOT/GLOB copies, XOBJ, XMTO, SIMI, HOUS, PERS, FAMh, SCOR and the
undecoded ids. Several of these will probably turn out persistent (SIMI/HOUS/PERS/XOBJ are in
the lot save), but nothing in this tooling established it. A name starting with `?` was
recalled from the community type list and not confirmed against game behaviour; the class never
depends on it. Candidates for transient to examine with real before/after saves: IMG in
Characters/Lots (62 MB, may be portraits or imposters), `.reia`, the `Thumbnails` and
`Storytelling` folders, and any time-stamp-bearing field inside SIMI/NGBH.

## Limits

- Classification is a first cut: most types are `unknown` and are treated as significant.
- Resource-level only for unparsed types: a change in a persistent blob is detected but not
  explained beyond byte ranges.
- A game save rewrites timestamps and may reorder or recompress; reordering and recompression
  are ignored, but state that legitimately changes inside "persistent" resources (for example
  a clock stored in NGBH or SIMI) will show up until those fields are found and masked.
- Non-package files are compared by bytes only; the whole-user-data mode has not been run on
  folders outside Neighborhoods (Config, Collections, ...), which currently classify as unknown
  unless they match a transient rule.
- Index minor 0/1 is implemented from the format description only (the E001 packages use
  minor 2); it is tested by a synthetic round-trip, not on a real file. The hole table is ignored.
- Python speed: about 35 s for a full 305 MB neighbourhood when files differ on disk.

## For the in-game save/reload comparison

Needed from an in-game run: a controlled pair of snapshots (user-data folder before; after save
and quit; after reload and re-save) from the same lot/state; a way to fix the clock and RNG so
simulation-driven fields stay equal; and one short session where only known things change
(move an object, give the family funds, change a sim skill) to confirm the parsers' field
meanings and find which unknown types (SIMI/PERS/XOBJ/OBJM) carry motives and time-stamps.

Snapshots (`scenario.ps1` `snap:`) and lotcheck fixtures hold hardlinks into the content-addressed store
local/snapstore (`tools/snapstore.py`, lane HS 2026-10-19): files read exactly as a copy (contents and modification
times), but a write into one in place reaches every snapshot sharing that file. Copy a snapshot before editing it
(robocopy and shutil copy contents), or call `snapstore.break_link(path)` first as `tools/setfunds.py` does;
`snapstore.py verify` finds an object that was written through.

## Field exclusions (`excluded` class)

`tools/sims2_types.py` `FIELD_EXCLUSIONS` lists byte ranges inside a resource that are known not to
carry state. A rule is added only once the field's meaning is established, and it carries the
reason and the evidence. A resource whose differences all fall inside its exclusions is reported
as `excluded` with the reason (not counted by `--fail-on`); otherwise the excluded bytes are masked
and the rest is reported under the type's class. Current rules:

| Type | Field | Why it is excluded |
|---|---|---|
| ?lot_aux_ACE46235 (nTSWorld::cProxyManager's serialisable GUID/string maps) | the dword after the type id and version 1 | uninitialised memory: the 0x18-byte map objects built in cProxyManager slot 3 (0x81aeb0..0x81af0f) never set +0x14; Write (0x81d0f0/0x81d190) saves it, Read (0x81bd90) only reads it back. Seen as heap-like values, 0x6c, "flag" (2026-10-11). |

## Reference fixtures (`tools/lotcheck.py`)
Seeded, frame-anchored runs of `tools/scenarios/lot-save-frames.txt` (`scenario.ps1 ... -ResetUserData
-Seed N`) end in a small set of states, in the original as well as with our replacements: the townie
generated on lot load has age 0x08 or 0x10 (the `age` property of E001_User00487's appearance
record), and within a state two lot objects take ids from 0x198..0x19B in varying order, the lot's
OBJM record (4F626A4D/1) refers to those ids, and ~100 of its bytes vary between runs. Reference runs
(`-Reference`) are recorded as fixtures, and a run is compared with each fixture of its age **as a
whole** (resources are never combined from different fixtures):

    python -I tools/lotcheck.py record  local/saves/<stamp>-saved   # reference runs; skips exact matches
    python -I tools/lotcheck.py check   local/saves/<stamp>-saved
    python -I tools/lotcheck.py recheck                             # every saved replacement run
    .venv/Scripts/python -I tools/tests/test_lotcheck.py            # negative tests of the gate (~10 min)

| Outcome | Exit | Meaning | Gate | `validate.sh` result |
|---|---|---|---|---|
| MATCH | 0 | identical to one fixture (no persistent/unknown difference, resource or file level) | accepted | PASS |
| MATCH-OPEN | 2 | identical except inside `KNOWN_OPEN` byte ranges, whose relation holds on both sides; printed as "MATCH-OPEN (open ranges held to their relation)" with the ranges | accepted: those bytes vary by nature, so they meet a bound and not an exact value | PASS |
| DIAGNOSTIC | 5 | MATCH or MATCH-OPEN, but against a backfilled fixture or by a run without a manifest | evidence, not acceptance | QUALIFIED |
| UNSEEN | 3 | no match, but every difference is where reference runs differ among themselves (or is a value a reference run produced) | not a pass: record more references or explain | QUALIFIED |
| UNEXPECTED | 1 | a difference where all references of the age agree, a package/resource added or missing, or a package that doesn't parse | blocks; a *confirmed regression* only once traced to our replacements | FAIL |
| NO-FIXTURE | 4 | no fixture with the same age and binding | record references first | FAIL |

The last column is the run's lot result, the one place it is set (`tools/validate_result.py` implements it; what the
results mean: `docs/orchestrator.md`, "Validation results"). Any other exit, a lotcheck that aborts (exit 1) or a
`lotsave` step with a nonzero exit is a FAIL too, whatever lotcheck says. Captured fixtures exist since 2026-11-09
(12 reference runs recorded: 8 at age 0x08, 4 at age 0x10, beside the 16 backfilled ones), so a run whose lot matches
one of them can read PASS; a run that matches only a backfilled variant still exits 5 (QUALIFIED). To add more:
`tools/scenario.ps1 @lot-save-frames -ResetUserData -Quiet -Seed 0x5eed0001 -Reference -NoDeploy`, then
`tools/lotcheck.py record <snapshot>`.

`KNOWN_OPEN` names an exact resource key and byte ranges: today only the neighbourhood camera
(EC44BDDC instance 0x262A, floats at 0x51 and 0x59..0x60; size must match; see below).
UNSEEN never passes: varying bytes show that exact matching is hard there, not that any value is
harmless, and a run whose lot objects come from one recorded variant and whose OBJM comes from
another is UNSEEN, not a match.

Fixtures are bound to their run conditions (`binding` in fixture.json): seed, the host's
`seed control:` lines, the scenario file's sha256 and the baseline user data's tree digest.
`scenario.ps1` writes `<stamp>-NAME.run.json` beside every snapshot with the scenario and baseline
digests; fixtures from before that (16, 2026-10-11/12) were backfilled from their logs, the scenario
at their git revision and the unchanged baseline. Only fixtures whose binding equals the run's are
used; runs without a manifest are compared on seed and controls only (the check says so).
`binding_source` records how a binding was made: "run manifest and host log" (captured by `record`
from the run itself) or "backfilled ...". Only a match against a captured fixture, by a run with a
manifest, is accepted (`check` exit 0 or 2); anything else that matches exits 5, DIAGNOSTIC. `list`
shows each fixture as captured or backfilled.
Fixtures live in `local/fixtures/lot-save/age-0xNN/<n>/` (game data, never committed).

### The neighbourhood camera record (EC44BDDC/0x262A, lane XK, 2026-11-06)

This was long filed as "the generated Sim's neighbourhood position". It is not: instance 0x262A is the name
`neighborhood` hashed, and the record is the neighbourhood camera's state. `t_cTSSaveNeighborhoodController::Step`
saves it through `cTSSGSystem::SaveEntry`, slot 77, to `cTSCameraSmoothSims1Controller`'s writer (0xb4aa40; reader
0xb48f30, from the load controller through slot 76).

Layout (115 bytes): 64 zero bytes; version byte 4; slot count 7; seven bookmarks, each a present byte and, when
present, the zoom (int index, byte, float), rotation (int index, byte), yaw (0x51), pitch (0x55), focus x, y, z (0x59,
0x5d, 0x61), two ints. Only the first is present. The yaw and focus belong to the camera's look-at point; z comes
from the controller's fixed height, so x, y are what moves, and pitch never does.

**Why they vary.** In the neighbourhood view with no input for 30 frames, `cCameraEffectsSupport` starts the drift
camera (option `CameraDriftCamEnabled`), the effect `nhoodcam`. It waits 3 seconds and then runs a meta-particle
effect with a single particle of life 5000 s: its position is given to a camera effect, which posts it to the
controller each frame. The particle does a horizontal random walk (two walks, about 3 and 2 units/s², drag 0.9),
drawn from the shared game generator 0x10fd138 and integrated in steps of up to 1/15 s of the effects clock, which
is real time. Any mouse or key event stops it, the camera stays at the last place posted, and the next drift starts
from there. So the focus is the record it loaded plus a random displacement that depends on how the frames fell:
the seed does not fix it, and `control_seed.cpp`'s virtual clock (simulator only) does not reach it. The yaw is the
drift effect's orbit curve (real-time too), folded into the yaw when the next camera effect starts, so it moves in
single jumps inside the curve's range.

The walk does not settle: its mean square displacement grows as about 37 per second, heading 0 at the start biases
x by about +7 per drift, and a simulation with the effect's constants gives rms 66, p99 144 for 100 s in 5 drifts.
The 77 sessions on disk with a manifest and a baseline: displacement 3.9..134.5 (median about 55), isotropic in y,
mean x +18..+37; turn -0.128..0.2245 rad; z and the bytes outside the ranges unchanged in all of them. Our runs lie
inside the references' spread.

**The relation** (`camera_session`, `CAMERA_TURN`, `CAMERA_MOVE`). The bytes cannot be compared exactly, so each side
is measured against the record *it* loaded (like the 0x173 counter: a reload's is its own first save's, kept in
`previous/`): every byte outside the ranges equal, values finite, turn in -0.36..0.52 rad (two curve ranges), and
displacement in 1..250 units. A run outside it is UNEXPECTED, and a fixture outside it cannot be matched. With no
baseline to measure from (`--bytes`, a run with no digest) nothing passes; a fixture whose own baseline is gone is
measured on the run's side only, and the open line says so.

**What it can catch.** A record restored wrongly (saved far from what was loaded), a drift camera that does not run
(saved exactly as loaded, or under 1), a walk off by a large factor, a broken height or pitch, a turn that was never
folded back to one range. It can't catch a walk off by a small factor: one sample of a random walk spans 4..134, so
the constants are held by the meta-particle differential tests, not here.

To settle the last doubt in game: a run with `CameraDriftCamEnabled` off should save this record byte-identical to
its baseline, and any other outcome means a second source.

## Normalised classes (`tools/lotcheck.py`, lane HA, 2026-10-18)

Before the byte comparison, `check` normalises the lot packages whose OBJM 4F626A4D/1 or object records
(XOBJ 584F424A, LOT_OBJECT FA1C39F7) differ, against the run's baseline (the folder its run manifest names,
used only when its tree digest still equals the run's `baseline_sha256`). Each class below has its meaning from
the code; anything in these records that does not fit stays a difference (`--bytes` turns normalisation off).
The report lists what was normalised and the numbers behind it.

**OBJM instance 1 layout** (`savediff.objm_layout`, writer cEdithObjectModule::vf5 0x42b370): 64 zero bytes;
vf111 (0x42ee60): 0, version 0xD8, 'OBJM', count, then `count` pairs (object id, type word: slot 57 of the
object's +0xf4 object) in insertion order; vf114 (0x42ec30): N and one word per object id 1..N from the module's
schedule table (+0x1a30; 0 for a free id); then the rest (unparsed, compared up to id words).

| Class | Meaning (code) | Compared as |
|---|---|---|
| Fresh object ids | AddObject 0x422910 gives an object without a requested id the lowest free id. The objects created during the run (not live in the baseline with the same type word) take different ids in different runs, and a different set of the free ids (0xf4/0xf5/0xfe/0x186 on lot 10). | Fresh objects matched by type word (one per type, else no match); baseline objects keep their ids. The mapping is completed to a permutation of ids; inside OBJM's list (fresh entries in any order), the schedule table and every record, a 16-bit word may differ only by run id vs mapped fixture id. |
| Records of non-live objects | The save writes the live objects' records (vf112 0x42ebf0 -> each object's slot 264) and deletes none: the records of objects deleted on load (0x187..0x189, and 0x186's staircase when no fresh object takes 0x186) are the input package's. | Must equal the baseline's record at the same key. |
| Schedule countdowns | Schedule word = flags << 16 \| countdown (vf71 0x42b6c0 / vf73 0x4280e0; flags vf74 0x42b9b0 / vf75 0x4283c0). The simulator's object pass (cTSSimulator vf4_11 0x483190) takes ids in order from a resume point: an object with flag 1 (and flag 2 while vf4_26 0x480fe0 is true) whose countdown is >= 1 is decremented, one whose countdown is < 1 has its thread run; a thread that returns false ends the pass, which resumes at that id. So a countdown records ticks to the object's next run, and its saved value depends on how many passes ran before the save (t: 1169..1392 in the re-saves, fewer under load). | Per side, t = the shift most counting entries (flags 1 and 2) share against the baseline (t - 1 above one id: the resume point). Entries without both flags must not move. |

A package is normalised as a whole: if any record contradicts the object table (a live object without its
record, a record that differs other than by the mapping, a stale record that is not the baseline's), nothing in
that package is normalised, even records byte-identical to the fixture's (records spliced from another run
under this run's OBJM fail this way). One exception: when the only thing unexplained is OBJM's plain schedule-id
entries (objects not kept from the baseline: the class the user accepted, notes/decisions.md 2026-11-06), the object
records are still normalised and OBJM alone stays a difference, judged against the references as bytes; otherwise a
per-load object's swapped id shows as a missing record (validation 20261109-190105-ea9ec3a8). Limit: the id comparison looks only at bytes that differ, so a run id
word that happens to equal an unrelated fixture id at the same offset is not caught (it would need field
knowledge of which words are ids).

### Reload leg (re-save of a re-save)

A run whose baseline is an earlier run's snapshot (a folder with its own `.run.json`) is a link in a chain:
`chain_of` follows the manifests' `baseline` keys to the prepared root. Such a run's state is `reload-N` (N =
links after the first save), it binds to the root's digest (`baseline_sha256`, so a replacement reload meets the
references' reload fixtures although each started from its own save) and records its immediate baseline's digest
as `immediate_sha256`; both are checked on disk before normalising. In the normalised comparison:

- per-load objects are named by type, from the reference chain: every type whose object is not at the same id
  in a save and the save it loaded (fixture vs its first save, first save vs root). On lot 10: 0x51, 0x112,
  0x118, one object each. All objects of those types are matched by type, whatever id they landed on: a reload
  deletes the first save's per-load objects (at 0xf4/0xf5/0xfe/0x186) and creates them again at free ids, which
  are sometimes the root's own 0x187..0x189 (so "not at its root id" would miss some). The other objects keep id
  and type on both sides. The set comes from the reference chain only, so a run that moves another object fails;
- a per-load object's XOBJ keeps its predecessor's id at 0x27e (the object of its type in the save it loaded:
  0x189 in every first save, the first save's id in a reload). The two chains' first saves hold those objects at
  different ids, so in a per-load object's records a word may also differ by the mapping between the two first
  saves' per-load objects (by type; "baselines' per-load objects matched" in the report);
- countdowns and the pass counter are measured on each side from the schedule and record that side loaded (its
  own first save: vf113 reads the schedule verbatim). A countdown entry may also differ when each side's value
  plus its passes equals the value it loaded (counted down from different saved values);
- records of non-live objects must equal that side's own previous save. `lotcheck record` copies a reload
  run's immediate baseline lots into `fixture/previous/` for this.
